# AuditGym

Воспроизводимая RL-среда для финансового аудита: генератор синтетических компаний с известными ошибками, контракт `reset`/`step` с пятью действиями и 100 шагами, отдельный процесс-оценщик и общая награда из кейса Genesis (FinTech); только стандартная библиотека Python, без сети, платных API и GPU.

## Проверка одной командой

```
docker build -t auditgym . && docker run --rm --network none auditgym
python3 -m auditgym check          # то же без Docker: Python ≥ 3.11, зависимостей нет
```

Команда запускает юнит-тесты, линтер детерминизма и таблицу `tools/score.py` (наше зеркало критериев кейса §10; это не оценка жюри) и печатает по фазам время и итог. Хвост вывода:

```
unit tests: 484 run (fast mode; --full also runs 8 more groups)
[tests: 61 s]
determinism lint: 0 problem(s)
Критерий                            Пройдено       Баллы
...
ИТОГО                                           100.0/100
[score table: 40 s]

total 101 s (fast mode)
CHECK: PASSED
```

Быстрый режим по умолчанию укладывается в две минуты (на нашей машине «total» = 101 с; число печатает сама команда). `python3 -m auditgym check --full` (в контейнере: `docker run --rm --network none auditgym python -m auditgym check --full`) добавляет все пропущенные тесты и четыре длинных инструмента: `tools.fuzz --seeds 100`, `tools.leakscan`, `tools.metamorph`, `tools.attack`; он занимает около четырёх минут (244 с на нашей машине; строка «total» в выводе). Команда по умолчанию в Dockerfile — быстрая: полный режим помещается в разумное время, но проверяющему нужен один короткий запуск, а полный запускается явно. Что именно пропускает быстрый режим и почему — `tools/check_modes.py`. Код возврата 0 только при `CHECK: PASSED`. Образ закреплён по digest (`Dockerfile`), в сборке и при запуске ничего не скачивается.

## Уровни сложности

`configs/levels.json` — четыре готовых уровня (`easy`, `medium`, `hard`, `max`); получить: `from auditgym.levels import load; env.reset(seed, load("hard"))`. Размер, страницы на полное чтение (от 7 до 49), шаги и возврат политик по уровням — `docs/RESULTS.md`, раздел «Уровни сложности» (`python -m tools.levels levels`).
Честно: бюджет 100 шагов не становится ограничением ни на одном допустимом конфиге (полное чтение — не больше 60 страниц по `MAX_PAGES`, на практике до 51), обрезано 0 эпизодов; рост сложности виден в штрафе 0.002 за шаг и в числе ошибок и проводок. Разбор — `docs/DESIGN.md`, раздел 10.

## Быстрый старт для политики

Политика — объект с `reset(observation)` и `act(observation) -> action`. Среда запускает процесс-оценщик сама; эталон живёт только в его памяти.

```python
from auditgym import Env
from policies.runner import make_policy      # любая политика из policies/

with Env(mode="train") as env:
    obs, info = env.reset(7, {"errors": {"duplicate_invoice": 1}})   # seed, config
    policy = make_policy("solver_policy")
    policy.reset(obs)
    done = False
    while not done:
        obs, reward, terminated, truncated, info = env.step(policy.act(obs))
        done = terminated or truncated
print(reward, info)   # 0.964 {'f1': 1.0, 'inspection_steps': 18, 'precision': 1.0, 'recall': 1.0, 'reward': 0.964}
```

Эпизод из каталога (файлы можно переставить и переименовать, это проверяет `tools/transform.py`): `env = Env.from_files("episodes/dev/ep_01"); obs, info = env.reset()`; `reset()` без seed начинает тот же эпизод заново. Режим `Env(mode="eval")` возвращает политике награду `0.0` и пустой `info`; настоящая награда пишется в журнал оценщика (`runs/results.jsonl`, права 0600, или `$AUDITGYM_RESULTS`).

Тот же оценщик по JSON-строкам (на каждый запрос одна строка в stdin и одна в stdout):

```
printf '%s\n' '{"op":"reset","seed":7,"config":{"errors":{"duplicate_invoice":1}}}' \
              '{"op":"step","action":{"action":"calculator","expression":"125000 * 465.37"}}' \
  | python3 -m auditgym serve --mode train
# вторая строка ответа: {"info":{},"observation":{"result":"58171250.00","steps_remaining":99,"type":"calculation"},"reward":0.0,"terminated":false,"truncated":false}
```

Действия: `list_records(table, cursor, limit ≤ 50)`, `get_record(table, id)`, `get_document(doc_id)`, `calculator(expression)`, `submit(findings)`; таблицы `ledger`, `invoices`, `payments`, `fx`. Схемы — `schemas/`, полный договор — `docs/CONTRACTS.md`.

Формат ответа в `submit`: сообщение `{"episode_id": ..., "findings": [...]}`. Голый список выводов `[...]` (в том числе пустой `[]`) принимается как выводы текущего эпизода. Объект без `episode_id` (например `{"findings": [...]}`) — не голый список, а сообщение без обязательного поля: неверная структура, награда −1 (CASE: неверная структура выводов).

## Конфигурация

Все ключи необязательны, неизвестный ключ — ошибка `unknown_key`; схема — `schemas/config.schema.json`, проверки — `auditgym/config.py`.

| Ключ | По умолчанию | Пределы |
|---|---|---|
| `size.invoices` | `[48, 100]`; если `size` не задан, растёт под число ошибок | от 10 до 200 |
| `size.background_pairs` | `[150, 300]` | от 0 до 1000 пар (две проводки каждая) |
| `currencies` | `["USD"]` (первая валюта, не равная базовой) | до 3 из `KZT, USD, EUR, RUB, CNY`, без базовой |
| `base_currency` | `"KZT"` | одна из пяти валют |
| `timezone` | `"+05:00"` | фиксированное смещение от −12:00 до +14:00, минуты 00, 30 или 45 |
| `period` | `{"start": "2026-10-01", "months": 1}` | начало `ГГГГ-ММ-01`, годы 2000–2100, месяцев 1–3; период — `[start, end)` |
| `errors` | по одной ошибке каждого типа, сколько позволяет плотность (`fx_error` — только при иностранной валюте) | число ≥ 0 на тип; всего ≤ 30 |
| `interaction` | `"none"` | `none`, `I1`, `I2`; сценарий добавляет две записи эталона к `errors` |
| `distractors` | `true` | `true` или `false` |
| `surface_seed` | `null` (берётся `seed`) | целое; другое значение даёт тот же эпизод с другими ID и порядком |
| `config_version` | `"1"` | только `"1"` |

Плотность: не больше одной ошибки на 8 счетов по нижней границе `size.invoices` (`INVOICES_PER_ERROR = 8`), то есть для N записей эталона нужно не меньше `8·N` счетов (но не меньше 10); максимум 25 ошибок при 200 счетах. Ещё: проводок ≤ 2 000, страниц на полное чтение ≤ 60. Нарушение — `ConfigError` с коротким кодом, через `Env` — `EnvError("bad_config")`, эпизод не создаётся. Таблицу «сколько счетов нужно на N ошибок» и все пределы печатает `python3 -m tools.config_table`:


## Ошибки и сценарии

Каждая ошибка — предикат над итоговыми открытыми записями; эталон — множество срабатываний, внесённое равно найденному (`auditgym/verify.py`, независимый решатель `auditgym/solver.py`). Формулы и правила проводок — `docs/DESIGN.md`. Вывод засчитывается, если совпали тип, множество `affected_ids`, валюта, сумма в допуске (`policy.amount_tolerance_minor`: 0, у `fx_error` 1 минимальная единица) и в `evidence_ids` (не более 10) есть полный набор доказательств.

| Тип | Определение | `affected_ids` | Сумма | Доказательства |
|---|---|---|---|---|
| `duplicate_invoice` | Два проведённых счёта с разными ID и одинаковыми контрагентом, валютой, итогом и позициями вместе с периодом услуги; `issued_at` в определение не входит | оба счёта (`doc_id`) | `total_minor`, валюта счёта | четыре набора `[счёт A, счёт B, строка A, строка B]`: по одной строке (Дт или Кт) из группы проводок каждого счёта |
| `allocation_gap` | У платежа есть строка на `unallocated`, платёж ссылается на счёт, а остаток дебиторки этого счёта после всех проводок больше нуля | платёж и счёт | `credit_minor` строки на `unallocated`, базовая валюта | платёж, счёт, строка `unallocated`, Дт дебиторки счёта, Кт дебиторки платежа |
| `fx_error` | Строка пересчёта (Дт дебиторки и Кт выручки у счёта, строка денег у платежа) отличается от `round(сумма × 10^(e_base − e_src) × курс даты документа)` больше допуска; курс берётся по дате документа в поясе компании | документ | модуль разницы, базовая валюта | `[документ, строка, ключ курса]` (ключ `дата\|ИСТ\|ЦЕЛЬ`), строка — Дт или Кт для счёта, деньги для платежа |
| `period_cutoff` | Документ датирован вне периода `[start, end)` в поясе компании, а его проводка стоит в книге периода (только это направление) | документ | сумма документа, валюта документа | `[документ, строка Дт]` или `[документ, строка Кт]` |
| `I1` | Частичный платёж в иностранной валюте у границы периода: `allocation_gap` и `fx_error` на одном платеже | платёж и счёт; платёж | как у входящих типов | как у входящих типов |
| `I2` | Копия счёта, датированная вне периода, но проведённая в нём: `duplicate_invoice` и `period_cutoff` | оба счёта; копия | как у входящих типов | как у входящих типов |

Законные случаи, которые остаются чистыми: переплата, аванс, частичная оплата, разбитый платёж, возврат, повторяющаяся сумма с другим периодом услуги, документ у границы периода в другом смещении, курс соседнего дня, выходные.

`heuristic` — демонстрационная эвристика без учёта отвлекающих случаев (частичные оплаты, позиции, пояс компании, переплаты): она ловит почти всё (R 0.948), но обвиняет и законные случаи (P 0.321, F1 0.470), на чистых книгах получает −1. Это не базовая политика и не часть баллов проверки.

## Gymnasium

`auditgym/gym_env.py` — обёртка `AuditGymEnv` над тем же `Env` (процесс-оценщик не меняется). Gymnasium не зависимость: без него модуль импортируется и работает, ядро его нигде не импортирует. Если gymnasium установлен, класс наследует `gymnasium.Env`, пространства — `spaces.Text` (наблюдение и действие — JSON-строки; действие можно дать и словарём), регистрируется `AuditGym-v0`.

```python
import gymnasium, auditgym.gym_env                        # импорт регистрирует AuditGym-v0
env = gymnasium.make("AuditGym-v0")                       # или AuditGymEnv.from_files("episodes/dev/ep_01")
obs, info = env.reset(seed=7, options={"errors": {"duplicate_invoice": 1}})   # options = config
obs, reward, terminated, truncated, info = env.step({"action": "calculator", "expression": "1+1"})
```

Проверено `gymnasium.utils.env_checker.check_env` (gymnasium 1.4.0 в отдельном venv; тест пропускается, если gymnasium нет).

## Экспериментальная награда с частичным баллом

Официальная награда разрежена: вывод засчитывается, только если совпало всё. Для исследований «как учиться на разреженной награде» есть отдельная **экспериментальная** величина `info["shaped_reward"]` (`auditgym/shaped.py`). Она **не входит в награду кейса**, не меняет `reward` и баллы проверок; по умолчанию выключена.
Включение: `Env(mode="train", shaped_reward=True)` (или `python3 -m auditgym serve --mode train --shaped-reward`). Значение приходит только в терминальном `info` режима train; в режиме eval опция игнорируется, и ключа нет ни в ответах, ни в журнале оценщика (CASE: подсказок по ходу нет).
Формула: частичный балл вывода за ошибку (тип совпал и есть общий `affected_id` — вес 2; `affected_ids` равны — 4; сумма в допуске и валюта — 2; доказательства достаточны — 2, всего 10), пары один-к-одному, `shaped = clip(2·F1' − 1 − 0.002·шаги)` с `F1' = 2·Σбаллы/(выводы + ошибки)`; при бинарных баллах совпадает с официальной наградой, неверная структура даёт −1. Значения политик — колонка «Shaped (эксп.)» в `docs/RESULTS.md`; вывод формулы — `docs/DESIGN.md`, §4.1.

## Как это устроено

Скрытая история компании → книги и документы, которые сходятся → операторы ошибок с записью в `provenance` → поверхность (непрозрачные ID, порядок записей) → открытые и закрытые файлы. Оценщик — отдельный процесс; политика видит только наблюдения. Подробности, формулы, версии и измеренный разбор сбоев — `docs/DESIGN.md`; договор между частями — `docs/CONTRACTS.md`; решения по аудиту — `docs/DECISIONS.md`, `docs/AUDIT.md`.

## Закрытая проверка

> **Для закрытого прогона задайте секрет оценщика — лучше файлом `AUDITGYM_SECRET_FILE`, а не значением `AUDITGYM_SECRET`.** Без секрета эпизод по seed и конфигурации воспроизводится кодом из этого репозитория: агент, который может импортировать `auditgym.generate`, переберёт малый seed и восстановит эталон (`python3 -m tools.seed_recovery`: seed 100 находится за 101 кандидата). Секрет оценщика подмешивается в каждый поток случайности, и по открытому коду без него эпизод не собрать. Воспроизводимость при этом сохраняется: **один и тот же секрет, seed и конфигурация дают побайтно один и тот же эпизод**, а смена секрета даёт другой. Значение нигде не печатается и не попадает в наблюдения, журналы и траектории.

**Где настоящая граница.** Секрет защищает эталон, только если политика не может его прочитать. Переменная `AUDITGYM_SECRET`, заданная в оболочке, видна каждому процессу, запущенному из неё, в том числе политике: это утечка по настройке, и код её не исправит. `Env()` запускает оценщик дочерним процессом под тем же пользователем, что и политика, поэтому сам по себе `Env` — удобство, а не граница. Граница — **оценщик в отдельном процессе под отдельным пользователем или в отдельном контейнере**: только он читает файл секрета и пишет журнал, а политика получает лишь два канала (stdin и stdout оценщика). Клиент секрет не читает: `Env(secret_file=PATH)` передаёт оценщику только путь и убирает `AUDITGYM_SECRET` из его окружения, а `Env(server_command=[...])` подключается к оценщику, запущенному чужой командой (журнал и секрет тогда настраивает эта команда, клиент добавляет только `--mode` и `--no-load`).

Рецепт: оценщик под пользователем `auditgym-eval` (Linux, команды от root один раз):

```
useradd --system --no-create-home auditgym-eval
install -d -o auditgym-eval -m 700 /etc/auditgym /var/lib/auditgym
head -c 32 /dev/urandom | od -An -tx1 | tr -d ' \n' > /etc/auditgym/secret
chown auditgym-eval /etc/auditgym/secret && chmod 400 /etc/auditgym/secret
cat > /usr/local/bin/auditgym-eval-serve <<'SH'
#!/bin/sh
# Только то, что добавляет Env: режим eval без load. Свой --mode train или --results политике не передать.
[ "$*" = "--mode eval --no-load" ] || exit 2
cd /opt/auditgym && exec /usr/bin/python3.11 -m auditgym serve --mode eval --no-load \
    --secret-file /etc/auditgym/secret --results /var/lib/auditgym/results.jsonl
SH
chmod 755 /usr/local/bin/auditgym-eval-serve
echo 'policy ALL=(auditgym-eval) NOPASSWD: /usr/local/bin/auditgym-eval-serve' > /etc/sudoers.d/auditgym
```

Код репозитория лежит в `/opt/auditgym` (владелец root, только чтение). Политика работает под пользователем `policy` и не может прочитать ни секрет, ни журнал:

```python
from auditgym import Env
command = ["sudo", "-n", "-u", "auditgym-eval", "/usr/local/bin/auditgym-eval-serve"]
with Env(mode="eval", server_command=command) as env:
    observation, info = env.reset(seed, config)   # seed и config выдаёт оркестратор жюри, не политика
```

Тот же оценщик в контейнере: `docker run -i --rm --network none -v /etc/auditgym:/run/auditgym:ro -v /var/lib/auditgym:/out auditgym python -m auditgym serve --secret-file /run/auditgym/secret --results /out/results.jsonl` — каналы этого процесса отдаются политике; сама политика при этом не должна иметь доступа к Docker (доступ к Docker равен root). Этот вариант мы не запускали: на машине разработки нет Docker; рецепт с `sudo` проверен тестом в упрощённом виде (`server_command` без смены пользователя, `tests/env/test_secret.py`).

**Журнал оценщика подписан.** Если задан секрет (или отдельный ключ `AUDITGYM_JOURNAL_KEY_FILE` / `AUDITGYM_JOURNAL_KEY`), каждая строка журнала получает `seq`, `prev` (подпись предыдущей строки) и `mac` — HMAC-SHA256 строки на ключе, выведенном из секрета (сам секрет в журнал не попадает). Цепочка продолжается через сессии, дописывающие один файл. Проверка:

```
python3 -m auditgym verify-journal /var/lib/auditgym/results.jsonl --secret-file /etc/auditgym/secret
```

Код 0 — все подписи и звенья верны; 1 — названа первая плохая строка (изменена, вставлена, переставлена, удалена или дописана без ключа); 2 — проверять нечего (журнал без подписи или ключ не задан, команда так и пишет). Чего подпись не ловит: строки, отрезанные с конца файла, и два оценщика, пишущих в один файл одновременно (давайте каждому свой файл). Подпись не прячет журнал: под тем же пользователем политика его прочитает и узнает награды, поэтому в закрытом прогоне журнал лежит у пользователя оценщика (рецепт выше). Строка `"event": "abandoned"` — эпизод, брошенный через `reset` после хотя бы одного шага, с потраченными шагами.

**Эталон для oracle под секретом.** `generate(seed, config)` без секрета строит другой эпизод, и oracle, взявший truth оттуда, получит −1. Выгрузите эпизод тем же кодом и тем же секретом, что у оценщика, и запускайте политики из каталога:

```
python3 -m auditgym export --secret-file /etc/auditgym/secret --seed <N> --config '{"errors": {"fx_error": 2}}' --out closed/ep_01   # или --config-file PATH
```

```python
from auditgym import Env
from auditgym.storage import load_episode
from policies.runner import make_policy, run_episode

truth = load_episode("closed/ep_01")["private"]["truth"]      # только на стороне оценщика
for name in ("random_explorer", "reconcile", "flag_all", "oracle"):
    with Env.from_files("closed/ep_01") as env:                # секрет для from_files не нужен
        print(name, run_episode(env, make_policy(name, truth=truth))["reward"])   # oracle: 1.0
```

Каталог в формате `episodes/train/*` (`public/` и `private/`), загружается через `Env.from_files`; без секрета в окружении он совпадает с `generate(seed, config)`. Секрет команда не печатает и не пишет в файлы, но `private/` содержит truth и seed: храните его на стороне оценщика, как и сам секрет.

Секрет мы намеренно не создаём сами: случайный секрет по умолчанию сломал бы детерминизм (CASE §54: повтор seed должен давать тот же эпизод), а открытые train и dev эпизоды обязаны собираться без него. Поэтому по умолчанию секрета нет, и `python3 -m auditgym check` печатает строку «AUDITGYM_SECRET: задан / не задан» и откуда он взят — из файла или значением (значение не печатается). Для закрытого прогона секрет нужен вместе с длинными скрытыми seed (не короче 128 бит, предел 256 бит). Решение и его цена — `docs/DECISIONS.md`, раздел H.

## Ограничения

- **Синтетические и упрощённые книги.** Данные генерируются, реальных финансовых данных нет. Только продажи и дебиторка: план из шести счетов, книга в базовой валюте, фиксированное смещение вместо часовых поясов, пять валют, синтетические названия и курсы, один–три месяца. Правило платежей (`policy.payment_rule`) — наша опубликованная модель, а не стандарт учёта; налогов, закупок, запасов и закрытия периода нет. Четыре типа ошибок и два сценария — единственное, что оценивается.
- **Seed можно восстановить перебором, если агент может импортировать пакет и seed мал.** `episode_id` — хэш открытых записей, а `generate(seed, config)` открыт, поэтому малый seed находится перебором: `python3 -m tools.seed_recovery` находит seed 100 за 101 кандидата (около 43 кандидатов в секунду на одном ядре при полной генерации; дешёвые фильтры по первым записям быстрее). Меры: `generate(seed, config, secret=...)` подмешивает секрет оценщика в каждый поток случайности (тест `tests/gen/test_generate.py`), а оценщик берёт его из файла `AUDITGYM_SECRET_FILE` / `--secret-file` или из переменной `AUDITGYM_SECRET` (тест `tests/env/test_secret.py`). Секрет, заданный значением в окружении политики, политика видит сама; граница — оценщик под отдельным пользователем или в контейнере (раздел «Закрытая проверка»). Для закрытого прогона задайте секрет (раздел «Закрытая проверка») и используйте длинные скрытые seed (не короче 128 бит, предел 256 бит). Без секрета открытые train/dev эпизоды воспроизводятся по seed и конфигурации.
- **Политика в том же процессе, что и запуск, видит seed.** `Env` держит оценщик в отдельном процессе, но `policies/runner.py` вызывает `env.reset(seed, ...)` в кадре, доступном коду политики, а код в том же процессе может импортировать `auditgym.generate`. В закрытом прогоне политику нужно запускать отдельным процессом и давать ей только наблюдения (протокол `serve`).
- **`inspection_steps` не включает шаг `submit`.** Oracle, который сдаёт ответ первым же шагом, получает `inspection_steps = 0` и награду ровно 1.0; если жюри считает и `submit`, та же награда будет 0.998. Мы читаем «шаги осмотра» буквально: считаются только действия до сдачи.
- **Обрезка по лимиту и тип суммы.** При `truncated=true` (100 шагов или лимит времени) ответ считается пустым и награда вычисляется по той же формуле: −1 на книгах с ошибками, `1 − 0.002·100 = 0.8` на чистых. `claimed_amount_minor` — целое число минорных единиц; целочисленный `float` (`125000.0`) читается как целое, дробное, строка или `bool` — неверная структура (−1).
- **Побочные строки курсовой ошибки.** Если `fx_error` внесена в счёт, у платежей этого счёта меняются строки `fx_difference`. Это следствие той же ошибки, а не отдельная ошибка: в эталоне она одна, и доказательств по этим строкам не требуется.
- **На книгах с ошибками молчание получает −1, и любая случайная угадка выше него.** Это свойство формулы кейса (`F1 = 0`, `2·0 − 1 = −1`), мы его не меняем. Следствие в таблице выше: «пометить всё» на книгах с ошибками набирает чуть больше молчания (`flag_all` минус `silence`: см. раздел «Проверки порядка» в `docs/RESULTS.md`), но на чистых книгах получает −1 против +1 у молчания и в среднем ниже его.
- **Результаты «пометить всё».** Лимит 30 выводов, плотность не больше одной ошибки на 8 счетов и точное совпадение множества ID дают точность около 0.005 и возврат около −0.99 на книгах с ошибками (таблица выше, `flag_all`); это измерение на наших эпизодах, а не доказательство, что обмануть награду нельзя.
- **Что награда не доказывает.** Награда сверяет вывод с нашим собственным эталоном: тип, ID, сумма и доказательства. Она не доказывает, что агент понимает учёт или обобщается на реальные книги; текст `explanation` на награду не влияет; решатель и oracle получают высокие значения по построению (эталон проверяется независимым решателем), поэтому высокая награда oracle не говорит о сложности среды. Дообучение модели мы не запускали, выигрыш от обучения на этой среде не измерен.
- **Платформа.** Проверено на macOS и в контейнере Linux (Python 3.11); Windows не проверялась (там `Env` передаёт путь журнала в командной строке вместо дескриптора).
