# Режим хакатона — Genesis FinTech, среда для ИИ-аудитора

Сроки, контрольные точки и правила — в `.claude/context/hackathon.md`. Кейс — в `docs/CASE.md`, ТЗ — в `docs/SPEC.md`, определения проверок организаторов (если опубликованы) — в `docs/CHECKS.md`.
Жюри ставит 90 из 100 баллов программой: доля пройденных проверок на закрытых эпизодах. Каждое действие должно либо делать зелёной ещё одну проверку `make score`, либо убирать блокер.

## Приоритеты
1. **Нет блокеров:** эталон не утекает, агент не пишет в оценщик, данные только синтетические, ядро запускается одной командой без сети (`/leak-hunt`, `/verify`).
2. **Контракт** из `docs/CASE.md` §03–§04 выполнен дословно.
3. **Эталон однозначен:** независимый решатель по открытым записям равен эталону на тысячах seed (`/fuzz-episodes`, `/error-type`).
4. **Награду нельзя обмануть** (`/reward-attack`), результат воспроизводим и не зависит от порядка и ID (`/metamorph`).
5. **Сдача собирается командами** и объяснена: README, записка о дизайне, измерения, ограничения (`/env-pack`, `/jury-readme`).
Если задача не двигает пункты 1–5, сначала согласуй её с пользователем. UI, обучение весов и «реалистичность» баллов не дают.

## Жёсткие правила кода
- Ядро (`auditgym/`) — только стандартная библиотека Python 3.11. Тесты на `unittest`.
- Случайность только через `auditgym.rng` (поток передаётся аргументом). Запрещены `random`, `uuid`, `os.urandom`, `time`, `datetime.now`, `hash()` для логики, обход `set` и `dict` без сортировки.
- Деньги — целые минимальные единицы; курсы и арифметика — `Decimal`; `float` запрещён.
- Определение ошибки — предикат над открытыми записями. Решатель не импортирует генератор ошибок, эталон и provenance.
- Эталон, provenance и seed живут только на стороне оценщика: не в наблюдениях, `info`, текстах ошибок, именах и путях, траекториях. ID назначаются после вставки ошибок.
- Тип записи определяется таблицей, а не видом ID. `affected_ids` и доказательства сравниваются как множества.
- Неверный ввод никогда не роняет среду: ограниченная ошибка и расход шага, либо награда −1 для неверной структуры выводов.
- Схемы в `schemas/` — общий контракт четырёх зон. Меняем только по согласованию и с повышением `schema_version`.

## Модели: где тратить токены
- Планирование и определения ошибок — на самой сильной модели (`/deep-plan`, `/error-type`).
- Реализация по готовому плану — агент `implementer` на каждый шаг, параллельно на разные зоны.
- Ревью и атаки — снова на сильной модели: `/hard-review`, агенты `code-auditor`, `ledger-auditor`, `env-attacker`, `tech-jury`.

## Как работаем
- Без SPEC и плана не кодим. Сначала проверка в `tools/score.py`, потом код, который делает её зелёной.
- Цикл: шаг плана → `/verify` → строка в `docs/SCORE-LOG.md` → коммит → push. Коммиты маленькие, Conventional Commits, на английском.
- Зоны файлов: `gen` (`world`, `books`, `inject`, `surface`), `env` (`env`, `serve`, `actions`, `calc`), `judge` (`matcher`, `reward`, `schemas` выводов), `qa` (`solver`, `verify`, `tools/`, `policies/`, документы). Чужую зону не правим: пишем владельцу.
- Guard-хук `.claude/hooks/guard.py` блокирует force-push, `reset --hard`, массовый откат, коммит `.env` и ключи. Блок — не повод обходить.
- Никаких платных LLM API и никаких сетевых вызовов в коде решения.
- Спорное место кейса: берём более строгое прочтение, записываем вопрос в `docs/QUESTIONS.md` и что делаем до ответа.
- Код, идентификаторы и коммиты — на английском; README и записка о дизайне — на языке кейса.
