# Использование AuditGym: подробности

Здесь то, что вынесено из `README.md` без изменений: проверка, уровни, протокол, конфигурация, ошибки, Gymnasium, экспериментальная награда, устройство. Закрытая проверка — `docs/CLOSED-RUN.md`, ограничения — `docs/LIMITATIONS.md`, перечень сдачи — `docs/SUBMISSION.md`.

## Проверка: подробности

Вне быстрого режима: мутационные прогоны `python3 -m tools.mutants` (судья) и `python3 -m tools.mutate_gen` (генератор и проверка данных: 44 мутации, 41 убита, 3 эквивалентные) и фазз `python3 -m tools.fuzz --seeds 10000` (180 000 эпизодов, 0 сбоев); подробности в `docs/DESIGN.md` §4.2.

**Время проверки.** Быстрый режим занимает около 4–7 минут в зависимости от машины, полный (`--full`) около 10–14 минут. Измерено: 235 с в Docker на двух ядрах, 386 с на Mac без контейнера, 314–349 с на двухъядерной машине GitHub Actions (Python 3.11, 3.12, Docker с `--network none`); точное число печатает сама команда в строке «total». Это единственное место с цифрами: `Makefile` и `Dockerfile` ссылаются сюда. `python3 -m auditgym check --full` (в контейнере: `docker run --rm --network none auditgym python -m auditgym check --full`) добавляет все пропущенные тесты и шесть длинных инструментов: `tools.fuzz --seeds 100`, `tools.leakscan`, `tools.metamorph`, `tools.attack`, `tools.mutants`, `tools.tricks --seeds 300 --check` (ловушки против простых трюков и решатель = эталон на 2 100 эпизодах, около двух минут); в Docker на GitHub Actions он занял 736 с (около 12 минут). Обе команды на каждый пуш запускает CI (`.github/workflows/check.yml`): Python 3.11 и 3.12, побайтная пересборка эпизодов и траекторий, сборка образа и запуск с `--network none`. Команда по умолчанию в Dockerfile — быстрая: полный режим помещается в разумное время, но проверяющему нужен один короткий запуск, а полный запускается явно. Что именно пропускает быстрый режим и почему — `tools/check_modes.py`. Код возврата 0 только при `CHECK: PASSED`. Образ закреплён по digest (`Dockerfile`), в сборке и при запуске ничего не скачивается.

## Результаты базовых политик: пояснения

Таблица со строками, которые сверяет `python3 -m auditgym check`, стоит в `README.md`; полная — `docs/RESULTS.md`.

`heuristic` — демонстрационная эвристика без учёта отвлекающих случаев (частичные оплаты, позиции, пояс компании, переплаты): она ловит почти всё (R 0.958), но обвиняет и законные случаи (P 0.236, F1 0.375), на чистых книгах получает −1. Это не базовая политика и не часть баллов проверки.

Колонка «Shaped (эксп.)» — экспериментальная награда с частичным баллом, не входит в награду кейса (раздел «Экспериментальная награда с частичным баллом»).

Возврат — `clip(2·F1 − 1 − 0.002·inspection_steps, −1, 1)`. Что из этого следует и чего нельзя вывести — в разделе «Ограничения».

## Уровни сложности

`configs/levels.json` — четыре готовых уровня (`easy`, `medium`, `hard`, `max`); получить: `from auditgym.levels import load; env.reset(seed, load("hard"))`. Размер, страницы на полное чтение (в среднем от 10 до 49), шаги и возврат политик по уровням — `docs/RESULTS.md`, раздел «Уровни сложности» (`python -m tools.levels levels`).
Честно: бюджет 100 шагов не становится ограничением ни на одном допустимом конфиге (полное чтение — не больше 60 страниц по `MAX_PAGES`, на практике до 51), обрезано 0 эпизодов; рост сложности виден в штрафе 0.002 за шаг и в числе ошибок и проводок. Разбор — `docs/DESIGN.md`, раздел 10.

## Быстрый старт: эпизод из каталога, протокол JSON-строк, действия

Эпизод из каталога (файлы можно переставить и переименовать, это проверяет `tools/transform.py`): `env = Env.from_files("episodes/dev/ep_01"); obs, info = env.reset()`; `reset()` без seed начинает тот же эпизод заново. Режим `Env(mode="eval")` возвращает политике награду `0.0` и пустой `info`; настоящая награда пишется в журнал оценщика (`runs/results.jsonl`, права 0600, или `$AUDITGYM_RESULTS`). `Env.from_files(..., mode="eval")` — только для разработки: оценщик режима `eval` по умолчанию отказывает на `load` (`bad_request`), клиент включает его флагом `--allow-load`, а строки журнала такого эпизода несут `"source": "load"` и `source_sha256`; `verify-journal` на них завершается кодом 1. Эпизоды закрытого прогона — только по seed (`Env(mode="eval")`).

Тот же оценщик по JSON-строкам (на каждый запрос одна строка в stdin и одна в stdout):

```
printf '%s\n' '{"op":"reset","seed":7,"config":{"errors":{"duplicate_invoice":1}}}' \
              '{"op":"step","action":{"action":"calculator","expression":"125000 * 465.37"}}' \
  | python3 -m auditgym serve --mode train
# вторая строка ответа: {"info":{},"observation":{"result":"58171250.00","steps_remaining":99,"type":"calculation"},"reward":0.0,"terminated":false,"truncated":false}
```

Действия: `list_records(table, cursor, limit ≤ 50)`, `get_record(table, id)`, `get_document(doc_id)`, `calculator(expression)`, `submit(findings)`; таблицы `ledger`, `invoices`, `payments`, `fx`. Схемы — `schemas/`, полный договор — `docs/CONTRACTS.md`.

Формат ответа в `submit`: сообщение `{"episode_id": ..., "findings": [...]}`. Голый список выводов `[...]` (в том числе пустой `[]`) принимается как выводы текущего эпизода. Объект без `episode_id` (например `{"findings": [...]}`) — не голый список, а сообщение без обязательного поля: неверная структура, награда −1 (CASE: неверная структура выводов).

## Конфигурация

Все ключи необязательны, неизвестный ключ — ошибка `unknown_key`; схема — `schemas/config.schema.json`, проверки — `auditgym/config.py`.

| Ключ | По умолчанию | Пределы |
|---|---|---|
| `size.invoices` | `[48, 100]`; если `size` не задан, растёт под число ошибок | от 10 до 200 |
| `size.background_pairs` | `[150, 300]` | от 0 до 1000 пар (две проводки каждая) |
| `currencies` | `["USD"]` (первая валюта, не равная базовой) | до 3 из `KZT, USD, EUR, RUB, CNY, JPY, KWD`, без базовой; разрядность 2, у JPY 0, у KWD 3 (`docs/DECISIONS.md`, M) |
| `base_currency` | `"KZT"` | одна из пяти валют |
| `timezone` | `"+05:00"` | фиксированное смещение от −12:00 до +14:00, минуты 00, 30 или 45 |
| `period` | `{"start": "2026-10-01", "months": 1}` | начало `ГГГГ-ММ-01`, годы 2000–2100, месяцев 1–3; период — `[start, end)` |
| `errors` | по одной ошибке каждого типа, сколько позволяет плотность (`fx_error` — только при иностранной валюте) | число ≥ 0 на тип; всего ≤ 30 |
| `interaction` | `"none"` | `none`, `I1`, `I2`; сценарий добавляет две записи эталона к `errors` |
| `allocation_gap_mode` | `"partial"` | `partial` (часть платежа осталась на `unallocated`, Кт дебиторки платежа меньше на разрыв), `missing` (платёж проведён, но не разнесён на счёт вовсе: всё закрытие ушло на `unallocated`, строки Кт дебиторки у платежа нет), `mixed` (вариант на каждую ошибку по случайному выбору). Касается только `errors.allocation_gap`; `I1` всегда частичный. Значение `partial` в нормализованный конфиг не пишется (`docs/DECISIONS.md`, S) |
| `distractors` | `true` | `true` или `false` |
| `surface_seed` | `null` (берётся `seed`) | целое; другое значение даёт тот же эпизод с другими ID и порядком |
| `config_version` | `"1"` | только `"1"` |

Диапазоны кейса (`docs/CASE.md`, §03: 200–2 000 проводок, 20–200 документов, 0–12 ошибок). **Проводки** — строки `ledger.csv`; **документы** — записи `invoices.jsonl` плюс `payments.jsonl` (с дублями и фоновыми, курсы `fx` не документы); **ошибки** — записи эталона. Конфиг по умолчанию, все 20 открытых эпизодов и все четыре уровня укладываются в эти диапазоны: `python -m tools.case_ranges` печатает размеры и PASS/FAIL, строка `case ranges` есть в `python -m auditgym check`. Число ошибок ограничено принудительно: итог (ошибки плюс 2 за I1/I2) больше 12 — `bad_config` (`too_many_errors`). Размеры пока шире (до 2 000 проводок, 200 счетов и ещё платежи), и их можно вывести за диапазоны кейса сознательно: например, `size.invoices = [10, 10]` без фона даёт около 27 проводок, а 200 счетов с дублями и фоном — до 400 документов.

Плотность: не больше одной ошибки на 8 счетов по нижней границе `size.invoices` (`INVOICES_PER_ERROR = 8`), то есть для N записей эталона нужно не меньше `8·N` счетов (но не меньше 10); но итог issues не больше 12 (то есть не больше 96 счетов нижней границы). Ещё: проводок ≤ 2 000, страниц на полное чтение ≤ 60. Нарушение — `ConfigError` с коротким кодом, через `Env` — `EnvError("bad_config")`, эпизод не создаётся. Таблицу «сколько счетов нужно на N ошибок» и все пределы печатает `python3 -m tools.config_table`:

```
errors | invoices needed (>=) | default size.invoices when size is omitted | accepted
     1 |                   10 |                                  [48, 100] | True
     8 |                   64 |                                  [64, 100] | True
    16 |                  128 |                                 [128, 128] | True
    25 |                  200 |                                 [200, 200] | True
    26 |                  208 |                                       None | no (bad_size)
```

## Ошибки и сценарии

Каждая ошибка — предикат над итоговыми открытыми записями; эталон — множество срабатываний, внесённое равно найденному (`auditgym/verify.py`, независимый решатель `auditgym/solver.py`). Формулы и правила проводок — `docs/DESIGN.md`. Вывод засчитывается, если совпали тип, множество `affected_ids`, валюта, сумма в допуске (`policy.amount_tolerance_minor`: 0, у `fx_error` 1 минимальная единица) и в `evidence_ids` (не более 10) есть полный набор доказательств. Эти правила по типам (какие документы, какая сумма и валюта, какие наборы доказательств) агент видит в первом наблюдении, в `task.answer_rules`: в нём же ключ курса `дата|ИСТ|ЦЕЛЬ` у `fx_error` и строки дебиторки у `allocation_gap`; блок одинаков во всех эпизодах и не содержит данных эпизода.

| Тип | Определение | `affected_ids` | Сумма | Доказательства |
|---|---|---|---|---|
| `duplicate_invoice` | Два проведённых счёта с разными ID и одинаковыми контрагентом, валютой, итогом и позициями вместе с периодом услуги; `issued_at` в определение не входит | оба счёта (`doc_id`) | `total_minor`, валюта счёта | четыре набора `[счёт A, счёт B, строка A, строка B]`: по одной строке (Дт или Кт) из группы проводок каждого счёта |
| `allocation_gap` | У платежа есть строка на `unallocated`, платёж ссылается на счёт, а остаток дебиторки этого счёта после всех проводок больше нуля | платёж и счёт | `credit_minor` строки на `unallocated`, базовая валюта | платёж, счёт, строка `unallocated`, Дт дебиторки счёта, Кт дебиторки платежа |
| `fx_error` | Строка пересчёта (Дт дебиторки и Кт выручки у счёта, строка денег у платежа) отличается от `round(сумма × 10^(e_base − e_src) × курс даты документа)` больше допуска; курс берётся по дате документа в поясе компании | документ | модуль разницы, базовая валюта | `[документ, строка, ключ курса]` (ключ `дата\|ИСТ\|ЦЕЛЬ`), строка — Дт или Кт для счёта, деньги для платежа |
| `period_cutoff` | Документ датирован вне периода `[start, end)` в поясе компании, а его проводка стоит в книге периода (только это направление) | документ | сумма документа, валюта документа | `[документ, строка Дт]` или `[документ, строка Кт]` |
| `I1` | Частичный платёж в иностранной валюте у границы периода: `allocation_gap` и `fx_error` на одном платеже | платёж и счёт; платёж | как у входящих типов | как у входящих типов |
| `I2` | Копия счёта, датированная вне периода, но проведённая в нём: `duplicate_invoice` и `period_cutoff` | оба счёта; копия | как у входящих типов | как у входящих типов |

Законные случаи, которые остаются чистыми: переплата, аванс, частичная оплата, разбитый платёж, возврат, повторяющаяся сумма с другим периодом услуги, документ у границы периода в другом смещении, курс соседнего дня, выходные.

## Gymnasium

`auditgym/gym_env.py` — обёртка `AuditGymEnv` над тем же `Env` (процесс-оценщик не меняется). Gymnasium не зависимость: без него модуль импортируется и работает, ядро его нигде не импортирует. Если gymnasium установлен, класс наследует `gymnasium.Env`, пространства — `spaces.Text` (наблюдение и действие — JSON-строки; действие можно дать и словарём), регистрируется `AuditGym-v0`.

```python
import gymnasium, auditgym.gym_env                        # импорт регистрирует AuditGym-v0
env = gymnasium.make("AuditGym-v0")                       # или AuditGymEnv.from_files("episodes/dev/ep_01")
obs, info = env.reset(seed=7, options={"errors": {"duplicate_invoice": 1}})   # options = config
obs, reward, terminated, truncated, info = env.step({"action": "calculator", "expression": "1+1"})
```

Проверено `gymnasium.utils.env_checker.check_env` (gymnasium 1.4.0 в отдельном venv; тест пропускается, если gymnasium нет).

## Экспериментальная награда с частичным баллом

Официальная награда разрежена: вывод засчитывается, только если совпало всё. Для исследований «как учиться на разреженной награде» есть отдельная **экспериментальная** величина `info["shaped_reward"]` (`auditgym/shaped.py`). Она **не входит в награду кейса**, не меняет `reward` и баллы проверок; по умолчанию выключена.
Включение: `Env(mode="train", shaped_reward=True)` (или `python3 -m auditgym serve --mode train --shaped-reward`). Значение приходит только в терминальном `info` режима train; в режиме eval опция игнорируется, и ключа нет ни в ответах, ни в журнале оценщика (CASE: подсказок по ходу нет).
Формула: частичный балл вывода за ошибку (тип совпал и есть общий `affected_id` — вес 2; `affected_ids` равны — 4; сумма в допуске и валюта — 2; доказательства достаточны — 2, всего 10), пары один-к-одному, `shaped = clip(2·F1' − 1 − 0.002·шаги)` с `F1' = 2·Σбаллы/(выводы + ошибки)`; при бинарных баллах совпадает с официальной наградой, неверная структура даёт −1. Значения политик — колонка «Shaped (эксп.)» в `docs/RESULTS.md`; вывод формулы — `docs/DESIGN.md`, §4.1.

## Как это устроено

Скрытая история компании → книги и документы, которые сходятся → операторы ошибок с записью в `provenance` → поверхность (непрозрачные ID, порядок записей) → открытые и закрытые файлы. Оценщик — отдельный процесс; политика видит только наблюдения. Подробности, формулы, версии и измеренный разбор сбоев — `docs/DESIGN.md`; договор между частями — `docs/CONTRACTS.md`; решения по аудиту — `docs/DECISIONS.md`, `docs/AUDIT.md`.
