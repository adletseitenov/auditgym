# /jury-readme

Читатель — инженер организаторов. Сначала он запускает проверку, потом ищет, почему что-то не прошло. README должен отвечать на оба вопроса за две минуты. Язык README — как в кейсе (русский), если организаторы не сказали иначе; идентификаторы и команды — как в коде.

## Структура
1. **Первый экран:** одна фраза, что это; одна команда запуска в контейнере без сети; что она печатает (таблица `make score` и таблица политик). Версия схемы и коммит.
2. **Что сдано** — таблица по `docs/CASE.md` §09: материал → путь в репозитории → команда, которая его пересобирает.
3. **Требования кейса → решение** — таблица: требование (короткая цитата) → модуль → тест или проверка. Каждая строка проверяема командой.
4. **Контракт:** `reset(seed, config)`, `step(action)`, пять действий с примерами JSON запроса и ответа, лимиты, ошибки, режимы train и eval, схема `config` с допустимыми диапазонами.
5. **Данные:** файлы эпизода и поля; как устроена история компании; четыре типа ошибок и два взаимодействия — определение, `affected_ids`, сумма, доказательства; отвлекающие случаи.
6. **Сопоставление и награда:** правила нормализации, допуски, выбор при равенстве, формула, пустые случаи; ссылка на код.
7. **Изоляция и воспроизводимость:** что именно гарантируется и какой проверкой подтверждается.
8. **Измерения:** таблица P, R, F1, возврата, шагов и времени для политик; результат `make fuzz` (число seed, брак); время генерации и шага.
9. **Ограничения** — честно: чем модель книг проще реальной, какие сочетания запрещены, чего награда не доказывает.
10. **Как подключить свою политику** — 10 строк кода.
11. Лицензия, использованные инструменты (включая AI).

## Правила
- Каждое число в README печатает команда из репозитория; рядом указана команда.
- Никаких обещаний о пригодности для реального аудита и об улучшении моделей.
- Режим skeleton: все разделы с TODO и уже работающая команда запуска.
